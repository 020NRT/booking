# Reserve — онлайн-бронирование столиков

Платформа для ресторанов Астаны: клиент выбирает ресторан, дату, время и **конкретный столик на интерактивной схеме зала**, вносит депозит и получает QR-код; ресторан управляет бронями, залом, меню и фото; администратор Reserve управляет всей платформой.

| Интерфейс | Адрес | Роль |
|---|---|---|
| Клиентский сайт | `/` | Customer (регистрация открыта всем) |
| Панель ресторана | `/partner` | Restaurant Admin (только свой ресторан) |
| Панель Reserve | `/admin` | Super Admin |
| Проверка QR | `/check/<token>` | сотрудник ресторана |

## Стек

- **Backend:** Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 15+ (нужно расширение `btree_gist`), JWT, bcrypt, Pillow.
- **Frontend:** React 19 + TypeScript, Vite, Tailwind CSS 4, Konva (схема зала), react-router.
- Прототип, с которого начиналась разработка, сохранён без изменений в [`legacy/`](legacy/). Его рестораны, меню и схемы залов перенесены в базу командой `python -m app.seed --demo`.

## Быстрый запуск (одна команда)

Нужны Homebrew-пакеты: `brew install postgresql@16 node python@3.13` (если ещё не стоят).

```bash
./scripts/start.sh
```

Первый запуск ставит всё сам (несколько минут): свою базу в `.pgdata` на порту 5433, зависимости, миграции, Super Admin и 3 демо-ресторана. Дальше запуск занимает секунды. Откройте http://localhost:5173. Остановка — Ctrl+C.

## Запуск локально вручную

Нужны: Python 3.12+, Node.js 20+, PostgreSQL 15+.

```bash
# 1. База данных
createdb reserve
createdb reserve_test   # для автотестов

# 2. Backend
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env    # заполните DATABASE_URL, JWT_SECRET, SUPERADMIN_* и т.д.
.venv/bin/alembic upgrade head
.venv/bin/python -m app.seed --superadmin   # создаёт Super Admin из .env
.venv/bin/python -m app.seed --demo         # 3 демо-ресторана (необязательно)
.venv/bin/uvicorn app.main:app --reload --port 8000

# 3. Frontend (в другом терминале)
cd frontend
npm install
npm run dev             # http://localhost:5173, /api проксируется на :8000
```

Пароли демо-администраторов ресторанов записываются в `backend/demo-credentials.txt` (файл в `.gitignore`).

Документация API (Swagger): http://localhost:8000/api/docs

## Продакшн

1. `cd frontend && npm ci && npm run build` → `frontend/dist`. Если папка существует, FastAPI сам отдаёт фронтенд, поэтому достаточно одного процесса: `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2`.
   Вариант: отдавать `dist/` через nginx, а `/api` и `/media` проксировать на uvicorn.
2. Обязательно: свой `JWT_SECRET`, `PAYMENT_WEBHOOK_SECRET`, `PUBLIC_BASE_URL` (домен с HTTPS, он попадает в QR-коды), `CORS_ORIGINS`.
3. Планировщик (освобождение неоплаченных броней, завершение визитов) работает внутри API (`RUN_SCHEDULER=true`). При нескольких серверах включайте его только на одном.
4. Резервные копии: `scripts/backup_db.sh` по cron (пример внутри скрипта), он архивирует БД и загруженные фото.

## Ключевые технические решения

**Защита от двойного бронирования** работает в три слоя:
1. Клиенту показываются только свободные столики (удобство, не защита).
2. Сервер заново проверяет столик, вместимость, рабочие часы и слот.
3. **В PostgreSQL стоит ограничение `EXCLUDE USING gist (table_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`** для активных статусов. Две пересекающиеся брони одного столика физически не могут попасть в базу. Перед вставкой берётся advisory-lock на столик, поэтому одновременные запросы встают в очередь, а проигравший получает понятный ответ 409, а не ошибку.

**Удержание на время оплаты:** бронь создаётся в статусе `pending_payment` с `hold_expires_at` (10 минут). Просроченные удержания освобождаются фоновым заданием и сразу при попытке брони того же столика. Подтверждение (`confirmed`) ставится **только** по подписанному серверному уведомлению провайдера. Повторные уведомления игнорируются (идемпотентность). Оплата, пришедшая после истечения удержания, подтверждает бронь, если столик ещё свободен, иначе автоматически уходит на возврат.

**Конструктор зала:** каждый столик — отдельная строка с UUID. Новые столики отправляются с `id: null` и вставляются новыми строками, существующие обновляются по id. Поэтому добавление столика не может заменить другой. Столик с будущими бронями удалить нельзя (его можно сделать недоступным), а столик с историей удаляется мягко.

**QR-код** содержит ссылку `/check/<token>`, где token — 256 бит случайности. Открыть и изменить бронь по нему может только авторизованный сотрудник **этого** ресторана.

**Безопасность:** bcrypt; JWT; роли проверяются на сервере в каждом запросе; регистрация всегда создаёт Customer; все запросы к БД через ORM с параметрами; фронтенд не вставляет HTML (React экранирует всё); изображения перекодируются Pillow в WEBP со случайным именем (EXIF удаляется); лимит попыток входа; заголовки безопасности; ошибки логируются с кодом, клиенту отдаётся код без деталей.
